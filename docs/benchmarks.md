# Measured benchmarks

Generated by `scripts/bench-scale.ps1`. One run each, not an average.
Corpora are built by `birds-eye-bench-corpus`.

These measure the `birds-eye-scan` CLI, not the desktop app, so they are floors.
Analysis runs at the AllOptIn budget, which is the most expensive tier.

Machine: LILITH, 24 logical cores. Recorded 2026-09-10.

Two rates are shown and they are not the same thing.
**end-to-end** is files divided by wall clock: the whole scan, index write included.
**walk only** is the scanner's own counter, which covers the directory walk and nothing after it.
Quote the end-to-end one unless you are specifically talking about the walk.

## Locked files

1,000 files held open exclusively by another process while the scan ran.

```
files indexed                 1000
files that got a sample hash     0   every one refused, as expected
scan_sessions.skipped_locked  1000   the uncapped truth
scan_issues rows               500   the capped sample list
```

The walk is unaffected: it reads directory entries, not file contents, so
`unreadable` is 0 and every file is indexed with correct metadata. Hashing is
what fails, and it fails cleanly - no group is formed from a file nobody could
read.

This case found issue #83: the hash-failure count was derived from the capped
row list, so 1,000 failures were reported as 500.

## Not measured

**Network files.** Roadmap Phase 11 asks for it and there is no share on this
machine to measure against. Not estimated, not guessed - simply not done.
Filed as its own item rather than left implied.

**Cold cache.** Every "scan ms" here is a warm first scan. There is no
supported way to drop the Windows file cache from a script without admin
rights and an external tool, so a genuinely cold number needs a reboot between
runs. Treat these as floors.

## What these numbers changed

Two of them were not measurements at first, they were bug reports.

- The 1,000,000-file scan originally ran **over seven hours** and produced zero
  duplicate groups. Cause and fix in issue #82; on the same data, membership
  went from a measured 10.0 hours to 5.9 seconds.
- The 100,000-image analysis originally ran **28 hours** without finishing.
  Half of that was a corpus whose images were all the same picture to a
  perceptual hash; the other half is issue #81, which is still open.

## Reading the table

Cost is per file, not per byte. 10.5 GB in 10,000 files scans in 3.3 seconds;
6.25 GB in 1,000,000 files takes 512 seconds. Anyone reasoning about scan time
should count files, not gigabytes.

The walk-only rate for images is low (5,053/sec) because those files are tiny
and numerous in deep directories; the walk-only rate is not a useful headline
figure in any case. Use end-to-end.
